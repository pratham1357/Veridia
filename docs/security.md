# Security Principles

Status: **design principles only. None of these controls are implemented yet.** They must be satisfied by the evidence-intake work in Phase 2.

Uploaded files are untrusted input and may be malformed or malicious.

| Principle | Requirement |
| --- | --- |
| File signature validation | Identify type from magic bytes; never trust the extension or client `Content-Type`. |
| File type validation | Allow-list of supported image formats; reject everything else. |
| File size limits | Enforce a maximum size while streaming, before the full file is read into memory. |
| Sanitized filenames | The original name is stored as display metadata only. |
| Path traversal prevention | Storage paths are generated by the server (e.g. from the evidence ID), never derived from user input. |
| Safe temporary storage | Isolated directory outside the web root and the repository, restrictive permissions, cleaned up after use. |
| No execution | Uploaded files are only parsed as data, never executed, imported or rendered as HTML. |
| Cryptographic hashing | SHA-256 computed at intake, recorded, and re-verifiable at any later point. |
| Preservation of originals | The original is stored read-only; analyzers work on it without modifying it and write derived artifacts separately. |
| Parser hardening | Image and metadata parsers process untrusted data; keep them updated and bound their resource use (e.g. decompression limits). |
